# Phase 2 Slice 1: Metrics In, Charts Out — Implementation Plan

**Status: completed** (12 October 2026, branch `metrics-slice`). Summary at the end.

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Any OpenTelemetry SDK sends metrics to Tracelet over OTLP/HTTP, and a user finds them, charts them with correct semantics (counter rates with reset detection, gauge aggregations, histogram quantiles), and groups them by service or attribute, through the HTTP API, `tracelet metrics`, and a Metrics view in the web UI.

**Tech Stack:** Go 1.27, `github.com/duckdb/duckdb-go/v2` (DuckDB 1.5.6), `go.opentelemetry.io/proto/otlp` v1.11.1 (`metrics/v1`, already a dependency), testify; React, TypeScript, TanStack Query and Router, Tailwind v4, vitest. **One new npm dependency: `uplot` 1.6.32**, the chart library DESIGN already decided on. No new Go dependencies.

## Design

### What this slice delivers

At the end, this works against a server set up as in the README quickstart:

```sh
# an OpenTelemetry SDK is pointed at http://localhost:8080 with an ingest token;
# it appends /v1/metrics itself, as it does /v1/logs and /v1/traces
tracelet metrics list --project shop --last 1h
tracelet metrics attributes http.server.request.duration --project shop
tracelet metrics query http.server.request.duration --project shop --aggregate p95 --group-by http.route --last 6h
tracelet metrics query orders.created --project shop --aggregate rate --group-by service
tracelet services --project shop                   # now counts metric points too
```

In the UI, a third view, **Metrics**, joins Logs and Traces. It lists the project's metrics. Opening one draws it as a uPlot time series, with controls for aggregation, grouping, filters, step, and range, all held in the URL.

Points flow exactly as logs and spans do. An OTLP/HTTP protobuf request arrives, and its token names the project. The server decodes and validates it, then converts it into `telemetry.MetricPoint` rows with a series hash. The rows go through the bounded queue to the single writer. The writer drops points already in the hot window and commits the rest, and only then is the request acknowledged. The hourly flush moves them to Parquet. Queries union hot and cold through one `query.Snapshot`. The `metric_points` table, its Parquet layout, flush, and retention already exist. This slice is the first to write and read them.

Out of scope:
- exponential histograms and summaries, which are rejected with a reason and backlogged;
- exemplars, which are dropped (phase 4);
- grouping by resource attributes;
- the overview page, dashboards, deployment markers, and alerts;
- OTLP/JSON and gRPC, unchanged from their backlog entries;
- a faster file layout for long metric queries. The storage spike measured a 24-hour counter rate at 1.7 s p50 at the `busy` workload. A 7-day range is several seconds there, which is inside the 30 s deadline. A personal project sends a small fraction of `busy`.

### Key decisions

1. **Series identity is the whole emitting context (fixes the spike's hash).** The spike hashed name, service, and point attributes. Two replicas of one service then share a series. Their cumulative counters interleave, and reset detection sees a false reset at every alternation. The series hash is now FNV-64a, with a zero byte after each field, over:
   - the project ID;
   - the metric name, type, temporality, monotonic flag, and unit;
   - the scope name, scope version, and scope attributes JSON;
   - the resource attributes JSON and the point attributes JSON.

   The JSON strings come from `jsonObject`, which marshals a map, so their keys are sorted and the encoding is deterministic. Resource attributes are fixed for an SDK's lifetime, so a series is one process's emission of one attribute set. `service.instance.id`, `host.name`, and `process.pid` all separate replicas without Tracelet having to know which keys identify an instance. Two instrumentation scopes that share a name but differ in version or attributes stay separate. A restart usually starts a new series. Decision 4 makes sure that costs no data. Temporality, monotonicity, and unit are part of the hash, so a configuration change never mixes delta and cumulative points in one series.

2. **Deduplication happens in the writer, against the hot window (the owner asked for a suggestion; this resolves the design's open decision).** An SDK retries a whole export when a response is lost after the commit. Inside the write transaction, before appending, the writer selects `series_hash, start_ts, ts` from hot `metric_points` rows in the batch's `ts` range whose `series_hash` is among the batch's. It then skips any point whose key is already there or earlier in the batch. Skipped points are counted as `duplicate_points` on health. This mirrors span deduplication, so there is one mechanism to understand. An export's points share one timestamp, so the lookup reads few rows.

   The alternative was keeping every row and deduplicating at query time. It was rejected because every query and every Parquet file would pay for it, and gauge averages would still be skewed. A retry that arrives after its hour was flushed is not caught. That is harmless for cumulative series, because the duplicate's delta is zero. It double-counts a delta series, a case accepted as rare and documented, as it is for spans.

3. **What is accepted, and what is refused.**
   - **Accepted:** gauges, sums (monotonic or not), and explicit-bucket histograms.
   - **Rejected with a reason, counted in `rejected_rows`, returned in partial success:**
     - exponential histograms ("exponential histogram metrics are not supported yet");
     - summaries ("summary metrics are not supported");
     - a sum or histogram without aggregation temporality;
     - a non-monotonic delta sum ("delta up-down counters are not supported"), because a level cannot be rebuilt from deltas without knowing where it started;
     - a point with no `time_unix_nano` or a timestamp past int64 nanoseconds;
     - a number point with neither value set;
     - a histogram whose `bucket_counts` is non-empty and not `len(explicit_bounds) + 1` long;
     - a metric with an empty name.
   - **Skipped silently:** a point flagged `NO_RECORDED_VALUE`. It carries no data, so nothing is discarded.
   - **Dropped:** exemplars.

   `ts` and `start_ts` are truncated to microseconds at conversion, which is DuckDB's `TIMESTAMP` resolution. A retried point's key then equals the stored row's key exactly, so deduplication matches it. Integer values stay in `value_int`. Gauges store temporality 0. A histogram without buckets is stored and contributes to `rate` and `avg`, but not to quantiles.

4. **Counter and histogram deltas follow the spike's verified CTE, with one change: a series that started inside the query's view counts its first point.** Per series, ordered by `ts`, a cumulative point is a reset when its value or count drops or its `start_ts` changes, and a reset's delta is its own value. Otherwise the delta is the difference from the previous point, element-wise for buckets. Buckets are never subtracted across a bounds change. Delta-temporality points are used as they are. A bounds change without a reset nulls only that point's bucket deltas. Its count and sum deltas still count, because they do not depend on the buckets. This differs from the spike, which dropped the whole point.

   The spike dropped every cumulative point without a predecessor. With per-process series (decision 1), that loses the first export after every deploy, which a low-traffic personal app notices. So a cumulative point with no predecessor counts its full value when its `start_ts` is at or after the start of the rows the query read. That means the series began inside the query's view and accrued everything since. The query reads from `from - 10 minutes` (`metricLookback`) so a window's first point finds its predecessor at default 60 s export intervals. Only deltas with `ts >= from` are kept.

5. **One query endpoint, aggregations by metric kind.** `GET /api/v1/metrics/query` takes `name`, `aggregate`, `group_by`, filters, `step`, and the range. Valid aggregations depend on the kind:

   | Kind | Aggregations (default first) | Meaning per step and group |
   | --- | --- | --- |
   | monotonic sum (counter) | `rate`, `increase` | sum of deltas, divided by the step in seconds for `rate` |
   | gauge, non-monotonic sum | `avg`, `min`, `max`, `sum` | per series per step reduce with the same function (`sum` takes each series' last point), then combine series with the function |
   | histogram | `p95` (any `pNN` or `pNN.N` in (0, 100)), `rate`, `avg` | quantile of merged bucket deltas; count deltas per second; sum deltas divided by count deltas |

   A name with no points in the range is a 404 naming the range. A name with more than one (type, monotonic, unit) kind in the range is a 400 that lists them and suggests a service filter. An aggregation the kind does not support is a 400 that lists the valid ones. Never sum cumulative samples, never average percentiles, never fill gaps: a step with no data is `null`, not zero.

6. **Histogram merging per group.** Within each group, the bucket bounds shared by the most distinct series over the whole window are the merged bounds. Ties go to the larger total count, then to the bounds that sort first, so the choice is deterministic. Series with other bounds are reported as `incompatible_series`, a count per group, and are not merged. Each step's quantile interpolates the merged bucket sums with the spike's `Interpolate`, which is ported unchanged with its edge tests.

7. **Steps are aligned integers, chosen automatically.** A step is `epoch_us(ts) // step_us` in SQL and the same integer division in Go. Steps therefore line up across queries regardless of DuckDB's `time_bucket` origin. With no `step`, the server picks the first of 10s, 15s, 30s, 1m, 2m, 5m, 10m, 15m, 30m, 1h, 2h, 3h, 6h, 12h, 24h that is at least `max(range / 200, 1m)`. That gives 1 h at 1m, 24 h at 10m, and 7 days at 1h. An explicit `step` must be at least 10s and yield at most 1,500 steps.

   The effective range starts at `from` aligned down to a step boundary, so the first step is complete and does not show a false dip. The response's `range` reports the aligned start. A point's delta covers the interval before it and is counted in the step that holds the point. Every step's `rate` is therefore its increase divided by the full step. The last step usually ends after `to` and holds fewer points, so it can read low until the step completes. DESIGN and the API description say so; the plan does not try to correct it, because any correction based on the time covered is wrong for points that carry a whole export interval.

8. **Results are aligned arrays.** The response carries `timestamps`, every step start in the range, and `series`, each `{group, values}` with one value or `null` per timestamp. That is uPlot's data shape and is easy for an agent to read. At most 20 series (`MaxMetricSeries`) come back. Groups are ranked by the sum of their non-null values, descending, then by group label. `truncated: true` says more existed. `group_by` is `service`, `environment`, `version`, or any point attribute key. A missing attribute groups under `""`.

9. **Discovery is two read endpoints.**
   - `GET /api/v1/metrics` lists the metrics in range: name, type, monotonic, unit, services, series count, point count, and last point time. It is filterable by `service`, `environment`, and a case-insensitive name substring `q`, and capped at 1,000 with `truncated`.
   - `GET /api/v1/metrics/attributes?name=` lists a metric's point attribute keys: up to 100 keys, each with its distinct-value count and its first 20 values in order.

   Both feed the UI's pickers and give agents what DESIGN promises: discover before you query. `GET /api/v1/services` gains a `points` count.

10. **The UI is a catalog plus a chart page, built from the existing pieces.**
    - `/metrics` is the catalog: a full-width list in the explore UI's style, with the FilterBar, a name filter, a service select, an environment filter, and the range picker.
    - `/metrics/$name` is the chart page. Its FilterBar holds aggregation, group-by (service, environment, version, then the attribute keys from discovery), service, environment, attribute filters, step (Auto or a fixed list), and the range.
    - The chart is a small uPlot wrapper. It reads colours from the semantic tokens (`--series-0..7`, `--line`, `--muted`), redraws when the `dark` class changes, never connects across `null` gaps, and formats axes by unit.
    - Below the chart, a legend list shows each group's colour, label, and value at the cursor, or the last value when the cursor is off the chart. Clicking a legend entry toggles that series.
    - Notices say when series were truncated or incompatible histogram series were left out.
    - Phones get a third tab.

    Logic that can be wrong silently lives in plain modules with vitest tests: search params, aggregation options per kind, the response-to-uPlot data conversion, and unit formatting.

### Data model

No schema change and no SQLite migration. `telemetry.MetricPoint` and the `metric_points` hot table and Parquet columns are as the logs slice created them. Only the meaning of `SeriesHash` changes (decision 1), and its comment is updated.

### HTTP surface

| Route | Scope | Purpose |
| --- | --- | --- |
| `POST /v1/metrics` | ingest | OTLP/HTTP metrics, `application/x-protobuf`, optional gzip, 4 MB limit; same handler as logs and traces |
| `GET /api/v1/metrics` | read | metric catalog: `project`, `service`, `environment`, `q`, `from`/`to`/`last` (default 1h) |
| `GET /api/v1/metrics/attributes` | read | attribute keys of one metric: `project`, `name` (required), `service`, `environment`, range |
| `GET /api/v1/metrics/query` | read | time series: `project`, `name` (required), `aggregate`, `group_by`, `service`, `environment`, repeatable `attr` (`key:value`), `step`, range |
| `GET /api/v1/services` | read | items gain `points` |
| `GET /api/v1/health` | none | `ingest` gains `duplicate_points` |

Catalog item: `{"name": "http.server.request.duration", "type": "histogram", "monotonic": false, "unit": "s", "services": ["api"], "series": 12, "points": 720, "last_ts": "..."}`. `type` is `gauge`, `sum`, or `histogram`.

Query response:

```json
{"name": "orders.created", "type": "sum", "monotonic": true, "unit": "{order}",
 "aggregate": "rate", "group_by": "service", "step_seconds": 60,
 "range": {"from": "...", "to": "..."},
 "timestamps": ["2026-10-12T10:00:00Z", "2026-10-12T10:01:00Z"],
 "series": [{"group": {"service": "api"}, "values": [4.0, null], "incompatible_series": 0}],
 "truncated": false}
```

`group` is `{}` without `group_by`. `incompatible_series` appears only for histogram quantiles. Errors are as for logs: `{"error": "..."}` with 400, 401, 403, 404, 413, 415, and 503 with `Retry-After`.

`ExportMetricsServiceResponse` has the same wire layout as the logs and traces responses: `partial_success` = 1, `rejected_data_points` = 1, `error_message` = 2. `otlp.PartialSuccess` therefore serves all three. Requests decode into `metricspb.MetricsData`, which is wire-identical to `ExportMetricsServiceRequest`.

### The deltas CTE, precisely

Ported from the spike (`git show 52c70cc:spike/storage/internal/query/metrics.go`), with the group column, histogram sums, the project and kind filters, and decision 4's first-point rule. `%s` is the Source subquery over `[from - metricLookback, to)`:

```sql
pts AS (
  SELECT series_hash, ts, start_ts, temporality, bucket_bounds, <group expr> AS grp,
         coalesce(value_double, value_int::DOUBLE) AS v, count::BIGINT AS c, sum AS s,
         bucket_counts::BIGINT[] AS b
  FROM %s
  WHERE project = ? AND name = ? AND type = ? AND monotonic = ? AND coalesce(unit, '') = ? <AND service = ?> <AND environment = ?> <AND attr filters>
),
lagged AS (
  SELECT *, lag(ts) OVER w AS prev_ts, lag(start_ts) OVER w AS prev_start, lag(v) OVER w AS prev_v,
         lag(c) OVER w AS prev_c, lag(s) OVER w AS prev_s, lag(b) OVER w AS prev_b,
         lag(bucket_bounds) OVER w AS prev_bounds
  FROM pts WINDOW w AS (PARTITION BY series_hash ORDER BY ts)
),
classified AS (
  SELECT *, temporality = 1 AS is_delta,
         prev_ts IS NOT NULL AND (start_ts IS DISTINCT FROM prev_start
           OR coalesce(v < prev_v, false) OR coalesce(c < prev_c, false)) AS is_reset,
         prev_ts IS NULL AND start_ts IS NOT NULL AND start_ts >= ? AS is_fresh,   -- the source's from
         prev_ts IS NOT NULL AND bucket_bounds IS DISTINCT FROM prev_bounds AS bounds_changed
  FROM lagged
),
deltas AS (
  SELECT grp, series_hash, ts, bucket_bounds,
         CASE WHEN is_delta OR is_reset OR is_fresh THEN v ELSE v - prev_v END AS dv,
         CASE WHEN is_delta OR is_reset OR is_fresh THEN c ELSE c - prev_c END AS dc,
         CASE WHEN is_delta OR is_reset OR is_fresh THEN s ELSE s - prev_s END AS ds,
         CASE WHEN is_delta OR is_reset OR is_fresh THEN b
              WHEN bounds_changed THEN NULL
              ELSE list_transform(range(1, len(b) + 1), lambda i: b[i] - prev_b[i]) END AS db
  FROM classified
  WHERE (is_delta OR is_reset OR is_fresh OR prev_ts IS NOT NULL) AND ts >= ?   -- from
)
```

Placeholders bind in textual order: the group expression's argument (an attribute's JSON path) comes before the Source arguments. The query builder assembles arguments in that order and has a test that a grouped, filtered histogram query returns the right numbers. The gauge path does not use this CTE. It reads the same Source with `ts >= from` and the same filters, unit included, reduces per series and step, then combines per group and step (decision 5).

Each request makes **one** `Source` call, over `[from - metricLookback, to)`, and reuses the subquery for the kind lookup and the data query, so the two agree (see `Source`'s comment on repeatable reads).

### Testing strategy

Tests sit at each boundary, as in the earlier slices:
- **Conversion:** hand-built `metricspb` messages.
- **Deduplication:** a real DuckDB store.
- **Queries:** the spike's semantics tests ported, every one run against hot and against flushed data through a real `Snapshot`, plus new tests for decisions 1, 4, 5, 6, 7, and 8.
- **Handlers:** fake auth and a fake ingester.
- **CLI:** a fake API.
- **End to end:** the app test gains a metrics scenario.
- **Frontend:** vitest for the pure modules.
- **Real SDK:** a throwaway program uses the real OpenTelemetry Go SDK, with two replicas, a restart, and delta and cumulative temporality, at known rates. The answers it should produce are computable, so the rates are checked against them, and then the UI is screenshotted.

## Completion summary

**Built.**
- **Ingestion.** `POST /v1/metrics` takes gauges, sums, and explicit-bucket histograms through the shared OTLP handler. Exponential histograms, summaries, delta up-down counters, and invalid points are rejected with a reason in the partial success response.
- **Series identity.** The series hash covers the project, the metric's name, type, temporality, monotonic flag, and unit, the scope, and the resource and point attributes, each field length-prefixed. Replicas and restarted processes are separate series.
- **Deduplication.** The writer drops points already in the hot window, keyed on series hash, start time, and time, and counts them as `duplicate_points`. Timestamps are truncated to microseconds at conversion so retries match.
- **Queries.** `GET /api/v1/metrics`, `/metrics/attributes`, and `/metrics/query` cover discovery and time series. Counters take `rate` or `increase`, gauges and up-down counters `avg`, `min`, `max`, or `sum`, and histograms `pNN`, `rate`, or `avg`. Steps are aligned, empty steps are null, and at most 20 groups come back.
- **CLI.** `tracelet metrics list`, `attributes`, and `query`; `services` counts points.
- **UI.** A Metrics catalog and a chart page drawn with uPlot in the semantic tokens, with a legend that toggles series, in light, dark, and phone layouts.
- **Dependency.** One new npm dependency, `uplot` 1.6.32.

**Reviews.** codex reviewed every task. The real findings were all fixed in follow-up commits:
- NUL bytes could merge two scopes' series (Task 1);
- integer counters lost precision past 2^53, and a group without deltas vanished (Task 6);
- a series switching between integer and double values lost its deltas (Task 6);
- a unit named like an Object prototype key formatted as NaN (Task 10);
- the chart froze its axis span and lone-point markers at construction (Task 11);
- tick spacings capped at a week dropped labels on long ranges (Task 12).

**Deviations**, as noted under each task:
- `rite` runs through `mise exec`;
- series hash fields are length-prefixed, and hashes are passed to SQL as text cast to `UBIGINT`;
- the catalog functions are `ListMetrics` and `ListMetricAttributes`, and an explicit step must be whole seconds;
- the deltas CTE subtracts integers as `HUGEINT`, and groups are seeded before the query paths run;
- the query tests share one snapshot per test;
- `FilterBar`'s search box is optional;
- the chart axis and legend changed after the screenshots.

**What the plan could have specified better:** the deltas CTE should have kept integer and double values apart from the start; the test helpers' habit of holding a gate slot per snapshot until the test ends should have been called out; and the chart's draw-time settings (axis span, lone points, tick spacing) needed a sentence saying they follow the data drawn, not the first render.

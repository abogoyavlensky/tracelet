# Phase 1 Slice 3: Explore UI — Implementation Plan

**Status: completed** (12 October 2026, branch `explore-ui`). Summary at the end.

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Task 4 is a **user checkpoint**: stop there and wait for the owner's choice.

**Goal:** A user signs in to the Tracelet web UI with an admin or read token, searches logs and spans, opens a trace as a waterfall with its span details and related logs, and moves between logs and traces by link. The UI is light by default with a dark toggle and works on a phone. The owner picks the visual design from 2–3 screenshotted variants before the real screens are built.

End-to-end sample data comes from `telemetrygen`, run with `go run` and not added to `go.mod`.

## Design

### What this slice delivers

At the end, against a running server:

1. Opening `/` without a session lands on `/login`. Pasting an admin or read token signs in. An HttpOnly cookie now carries the session, and the browser lands on `/logs`.
2. **Logs** (`/logs`): newest first, with filters for project, service, environment, minimum level, body text, and `key:value` attributes, plus a time range (presets or absolute). "Load more" follows the cursor. Selecting a record shows all its fields, resource, and attributes. A record with a trace ID links to its trace.
3. **Traces** (`/traces`): span search with "root spans only" on by default, which works as a list of traces. Filters cover service, environment, span name, status, minimum duration, and attributes. Each row shows its duration and status and opens the trace.
4. **Trace** (`/traces/$traceId`): a header with ID, start, duration, services, and span count. Below it are the waterfall (nested by parent, offsets and widths to scale, errors highlighted) and the selected span's details: attributes, resource, events, and links. Related logs come next, oldest first, and can be narrowed to the selected span. A truncated trace or one with orphan spans says so.
5. A header has the project picker (hidden for a project-scoped token), navigation, a health dot from `/api/v1/health`, the light/dark toggle, and sign-out.
6. Every view's state (project, filters, time range) lives in the URL, so a copied link reopens the same view. A shared URL still requires sign-in.

Out of scope:
- **Live log tail.** It gets a backlog entry.
- **Auto-refresh.** A refresh button re-runs the query.
- **The Overview and dashboards.** They need metrics.
- **Charts.**
- **OTLP/JSON.** It stays a separate slice in its backlog entry.
- **User accounts.**
- **Token and project management in the UI.** The CLI covers both.

### Key decisions

1. **Signing in uses an existing token instead of a setup URL and user account. This amends a decided item at the owner's request.** DESIGN's "UI bootstrap (decided)" has a one-time setup URL create an admin user. Tokens already exist, the bootstrap already prints an admin token (or stores `TRACELET_ADMIN_TOKEN`), and a single-owner tool gains nothing from a second credential type. These endpoints change:
   - `POST /api/v1/session` takes `{"token": "tl_..."}` and authenticates it through the existing `Authenticator`. An `admin` or `read` token gets 200 with the session body below, plus a `Set-Cookie`. An `ingest` token gets 403 ("ingest tokens cannot sign in"); an unknown or revoked one gets 401.
   - `GET /api/v1/session` (read scope, cookie or bearer) returns the session body. The UI calls it on load, and the CLI could use it as a whoami.
   - `DELETE /api/v1/session` clears the cookie and answers 204. It needs no authentication.

   The session body is:
   ```json
   { "scope": "admin", "token_name": "bootstrap admin", "project": "shop", "projects": [{ "slug": "shop", "name": "Shop" }] }
   ```
   `project` is present only for a project-scoped read token. `token_name` lets the header show which token the browser is signed in as.

   **Use one token per browser (agreed with the owner).** The recommended practice is to create a token for each browser instead of reusing the bootstrap admin token:
   ```sh
   tracelet tokens create --scope admin --name laptop
   tracelet tokens create --scope read --name phone
   ```
   Losing a device then means revoking one token, not rotating the admin token everything else depends on. A read token is enough for everything this slice's UI does. The sign-in page, the README, and DESIGN all recommend this. The bootstrap token still works, for the very first sign-in. `projects` lists what the token can read: every project for admin and all-project read tokens, and only its own for a project-scoped one. `scope` is `admin` or `read`.

2. **The cookie holds the token itself, not a session ID.** The cookie is `tracelet_session=<token>; Path=/api/; HttpOnly; SameSite=Strict; Max-Age=2592000` (30 days). `Secure` is set when the request arrived over TLS (`r.TLS != nil`) or `X-Forwarded-Proto` is `https`, which is how Caddy forwards in the deploy. Plain-HTTP local runs therefore still work. Revoking the token ends every browser session on the next request, with no sessions table or migration. `Path=/api/` keeps the cookie off asset requests. The token never reaches JavaScript or `localStorage`.

3. **Cookie authentication is limited to the management API and protected against cross-origin writes.** `requireScope` takes the credential from `Authorization: Bearer` when present, and otherwise from the cookie, but only for paths under `/api/`. OTLP routes (`/v1/`) never accept the cookie. When the credential came from the cookie, the request also goes through `http.CrossOriginProtection.Check`, which refuses non-safe cross-origin browser requests (it is a no-op for GET and HEAD). Bearer requests skip the check, so the CLI and SDKs are unaffected, and a future browser OTLP exporter is not blocked. `SameSite=Strict` is the first line of defence; the check is the second.

4. **The visual design is chosen from variants before the real screens are built.** Task 2 builds the shared, design-neutral base: router, theme mechanism, API types, fixtures, and pure logic. Task 3 builds three variants of the two screens that matter, the logs explorer and the trace page, on dev-only prototype routes fed by fixtures:
   - **A, dense table.** A log-viewer look: compact monospace rows, a single filter bar, details expanding inline.
   - **B, split pane.** The list on the left and the selected record or trace detail on the right, like a mail client. On a phone this becomes list, then detail.
   - **C, calm cards.** Roomier rows, a left sidebar for navigation, and severity colour as the main signal. The detail opens in a side drawer, or full screen on a phone.

   Task 4 screenshots each variant in the preview browser and stops for the owner's pick. The owner may also mix variants. Task 5 promotes the choice into the real theme tokens and components. Tasks 6–8 build real screens in that design, and Task 9 deletes the prototypes. The variants differ in layout and density, not just colour. Each one has its own light and dark token values, scoped to its wrapper.

   **Chosen design (12 October 2026): variant D**, a mix the owner asked for after seeing A, B, and C, and then D itself. It has:
   - **Header:** B's top header (the three-bar mark, project picker, Logs/Traces segmented control, time range, refresh, health dot, theme toggle, token menu) and B's cobalt palette (`VariantB/tokens.css`).
   - **Logs:** A's full-width one-line rows under a full-width filter bar (service, environment, level, search, attribute). Only warn, error, and fatal rows get a coloured left edge. Selecting a record opens a detail pane on the right (44%, 420–760 px). The list only narrows and drops its service column; it never moves. j/k move the selection, and Esc or ✕ closes the pane.
   - **Trace:** B's summary strip above a full-width waterfall with A's hairline time grid (five tick labels and gridlines) and hatched error bars. Selecting a span opens the same pane. A trace with an error opens with its first failed span selected and the pane open.
   - **Phones:** B's bottom tab bar and list-to-detail push with a back button. The trace page starts on the waterfall.
   - **Navigation:** the top header stays for this slice. An icon rail replaces it when phase 2 adds Overview, Errors, and Dashboards, so the shell is one component with a list of nav items.
   - **Brand:** B's three-bar mark is the brand icon and the favicon (`web/public/favicon.svg`, with a lighter blue for dark browser themes).

5. **Light is the default and dark is a toggle.** Colours are semantic tokens: CSS variables on `:root` and `.dark`, exposed to Tailwind v4 through `@theme inline` (classes such as `bg-surface`, `text-muted`, `border-line`). Components never use raw palette classes like `slate-950`. Dark mode is the class variant `@custom-variant dark (&:where(.dark, .dark *))`. The choice (`light` or `dark`) is stored in `localStorage` under `tracelet.theme`. A small inline script in `index.html` applies it before the first paint, so there is no flash. Without a stored choice the theme is light, as the owner asked, and it does not follow the OS setting.

6. **Mobile-first layouts at one breakpoint (`md`, 768 px).** Below it, lists render as stacked cards, filters fold behind a "Filters" button, and details take the full screen. The waterfall gets its own narrow layout: each span is a name line (indented by depth, with duration) above a full-width timing bar, instead of a name column beside a bar column. Touch targets are at least 40 px.

7. **Routing is code-based TanStack Router, with search params validated by hand-written functions.** The routes are:

   | Path | Purpose |
   | --- | --- |
   | `/login` | Sign-in form |
   | `/` | Redirects to `/logs` |
   | `/logs` | Logs explorer |
   | `/traces` | Span search, root spans only by default |
   | `/traces/$traceId` | Trace page |

   An authenticated layout route loads the session with `queryClient.ensureQueryData` in `beforeLoad` and redirects to `/login` on 401. The project is a search param (`?project=shop`), not a path segment: `/api/` and `/v1/` already belong to the server, so a slug such as `api` would collide with a path segment. Without `project` in the URL, the app uses the token's own project, then the last one used (stored in `localStorage`), then the first project.

8. **Time ranges in the URL are either relative or absolute, mirroring the API exactly.** `last=1h` (relative) or `from` and `to` (RFC 3339). With neither, the API's default applies. Presets are 15m, 1h, 6h, 24h, and 7d. The URL and the API carry Go durations, because the API parses `last` with `time.ParseDuration`, which has no `d` unit. The 7d preset is therefore `last=168h`, and "7d" is only its label. "Custom" uses two `datetime-local` inputs in the browser's zone. DESIGN asks for absolute ranges in URLs; this slice keeps relative ones in the explorer, because "the last hour" is what a bookmark should mean. Every link between views is absolute, so following one is reproducible:
   - **Log to trace and span row to trace:** `from` is the record's `ts` minus 1 day and `to` is `ts` plus 1 day. A trace stays fully inside that range, which also bounds the lookup scan.
   - **Trace to related logs:** `trace_id` with `from = trace.start` and `to = trace.end + 1s`, as the API documents. Pages hold 500 logs, newest first from the API, and the loaded logs are shown oldest first. While `next_cursor` is present, a notice says "Showing the newest N logs of this trace", and "Load older" fetches the next page. "Only this span" filters the loaded logs by `span_id` on the client. When older logs are still unloaded, its empty state reads "No logs for this span among the N loaded" rather than "No logs".

9. **Pages load with `useInfiniteQuery`; the cursor stays out of the URL.** "Load more" appends the next page while `next_cursor` is present. A page after the first sends the original filters plus `cursor`, and never `last`, `from`, or `to`, because the API refuses that combination and the cursor carries the range itself. The resolved `range` from the response is shown, so a relative range displays the absolute window it searched. A 401 from any query clears the session cache and redirects to `/login`. A 503 shows the server's message along with its `Retry-After`.

10. **The waterfall is built from the flat span list by a pure, tested function.** `buildWaterfall(trace)` nests spans by `parent_span_id`. Children are sorted by `ts`, then `span_id`. Spans whose parent is missing (not yet exported or truncated) become extra roots, flagged as orphans. A cycle (malformed data) is broken by visiting each span once. For each row the function computes `depth`, `offsetPct`, and `widthPct` relative to `trace.start` and `trace.duration_ns`, with a minimum visible width of 0.5%, and a stable colour index per service. A zero-duration trace gives every bar the minimum width at offset 0.

11. **Only pure logic gets frontend tests.** The vitest environment stays `node`. Tests cover the parts that can be wrong silently: waterfall building, search-param validation, time-range conversion, and formatting (durations from ns, severity names, timestamps). Components are checked by the screenshot passes in Tasks 4 and 10 instead of jsdom tests, which would mean new dependencies (`jsdom`, Testing Library). Go gets full tests for the session endpoints and cookie authentication.

12. **No other new dependencies.** There is no icon library: the dozen icons needed are inline SVG components. There are no web fonts: the system UI stack and the system monospace stack are used. The router's devtools are left out.

### Session endpoint behaviour, precisely

| Request | Result |
| --- | --- |
| `POST /api/v1/session` with an admin or read token | 200, session body, `Set-Cookie` as in decision 2 |
| ... with an ingest token | 403 `{"error":"ingest tokens cannot sign in"}`, no cookie |
| ... with an unknown or revoked token, or malformed JSON | 401 or 400, no cookie |
| `GET /api/v1/session` with a valid cookie or bearer | 200, session body |
| `GET /api/v1/logs` with only a valid cookie | 200, as with bearer |
| `POST /api/v1/projects` with an admin cookie and `Sec-Fetch-Site: cross-site` | 403 from the cross-origin check |
| `POST /api/v1/projects` with an admin cookie and `Sec-Fetch-Site: same-origin` | 201 |
| `POST /v1/logs` with only an ingest token in the cookie | 401, because OTLP ignores the cookie |
| Both bearer and cookie present | The bearer wins |
| `DELETE /api/v1/session` | 204, `Set-Cookie` with `Max-Age=0` and the same path |

## Completion summary

**Built.** The web UI is no longer a status card:
- **Sign-in.** It uses an existing admin or read token, carried in an `HttpOnly`, `SameSite=Strict`, `Path=/api/` cookie that holds the token. Revoking the token ends the session, OTLP ignores the cookie, and cookie-authenticated writes pass Go's cross-origin check. The session endpoints are `POST`, `GET`, and `DELETE /api/v1/session`, with Go tests for every case and a browser sign-in step in the end-to-end test.

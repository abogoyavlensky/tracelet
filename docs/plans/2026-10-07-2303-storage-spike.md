# Storage Spike (Phase 0) Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prove or disprove the hot/cold DuckDB + Parquet storage layout from `docs/DESIGN.md` with measurements: crash-safe flush, retention that reclaims disk, ingestion under heavy queries, trace lookup latency, metric semantics, backup equivalence, and CGO release builds on both Linux architectures, all inside the 1 GB budget.

**Tech Stack:** Go 1.27, `github.com/duckdb/duckdb-go/v2` v2.10506.0 (DuckDB 1.5.6, bundled static libraries, CGO), `modernc.org/sqlite` for the manifest, testify, rite tasks, GitHub Actions matrix on `ubuntu-24.04` and `ubuntu-24.04-arm`.

---

## Design

### Why this spike exists

`docs/DESIGN.md` marks the hot/cold storage split as **decided**, but every number attached to it is a guess: the one-hour hot window, the 256 MB DuckDB memory limit, trace lookup by time-bounded scan, and the claim that retention becomes a file delete. Phase 1 builds on all of them. This spike builds the smallest real version of the storage path, drives it with synthetic telemetry for seven simulated days, and measures the seven items in the design doc's validation checklist. The output is a results note and an updated design doc, not product code.

### Scope

In scope: DuckDB hot tables, the Appender write path, hourly Parquet flush with a SQLite manifest, crash reconciliation, retention and ring-buffer deletion, a query builder that unions hot and cold, counter and histogram SQL, backup and restore, a load generator, a CLI that runs the scenarios and prints a JSON report, a CI build on both Linux architectures, and the results note.

Out of scope: HTTP, OTLP decoding, authentication, projects, the UI, duplicate handling, rollups, and the trace index fallback. Duplicate handling needs the ingestion path's shape and is a phase 1 design task; the spike records the Appender throughput so that decision has a baseline. The trace index is built only if the measured lookup fails its threshold, in a follow-up.

### Key decisions

1. **Separate Go module at `spike/storage/`.** Its own `go.mod` keeps DuckDB and CGO out of the main binary until phase 1 adopts them deliberately. The main module's `rite check` stays fast; spike tasks are `spike-check`, `spike-build`, `spike-run`. The directory is deleted or archived when phase 1 starts.
2. **`duckdb-go` with bundled static libraries.** This is the single-file path the design assumes and what pagelet already ships. The CI matrix confirms it links on amd64 and arm64 and records the binary size. Dynamic linking (`duckdb_use_lib`) is the fallback only if static fails.
3. **Attributes as `VARCHAR` holding JSON text, not DuckDB's `JSON` type.** The Appender marshals `string` values into JSON strings, so pre-serialised JSON would be double-encoded, and Parquet has no JSON type anyway. DuckDB's `json_extract` functions accept `VARCHAR`.
4. **Cold files resolved from the manifest, not a glob.** The query builder asks the manifest for the files covering `[from, to)` and emits `read_parquet([...], union_by_name = true)`. This gives exact partition pruning, avoids a view that breaks when no file matches, and means the manifest is load-bearing, so the spike tests it for real.
5. **Manifest in SQLite via `modernc.org/sqlite`.** Pure Go, no second native dependency. The product's SQLite driver choice stays open; the manifest workload is tiny either way.
6. **Reconciliation adopts orphan files.** A crash after rename but before the manifest insert leaves a complete, fsynced Parquet file that no one knows about. Reconcile reads its row count, time range, and ingest cutoff from the file and inserts it, then deletes only the hot rows that file covers. Temporary files (`*.parquet.tmp`) are deleted. Manifest rows whose file is missing are removed. Reconcile has no retention policy; retention runs right after it at startup, so expired orphans are adopted and then deleted by the normal path.
11. **Every exported row is identified by its ingest stamp.** The writer stamps `ingest_ts` on every row of a batch, strictly increasing across batches (a batch never gets a stamp at or below the previous batch's). A flush exports the rows of one hour whose `ingest_ts` is at or below a cutoff captured in the same `COPY` statement, records that cutoff in the manifest as `max_ingest_ts`, and deletes exactly `ts in hour AND ingest_ts <= cutoff`. Late rows that land in the hour after the cutoff survive and flush into a second file later. This is what makes reconciliation and backup correct without pausing ingestion: with one writer committing in stamp order, any row visible to `COPY` has a stamp at or below the cutoff and any row committed later has a higher one.
12. **A brief duplicate window during flush is accepted for the spike.** Between the manifest insert and the hot `DELETE`, a query can see an hour's rows twice. The window is the duration of one `DELETE`, which the report records. Reordering to delete before recording would turn the duplicate into a brief gap instead; neither is atomic because the two databases do not share a transaction. Phase 1 decides which to prefer with the measured window in hand.
7. **Simulated clock for volume, real clock for latency.** A seven-day run with an accelerated clock measures volume, disk, flush cost, and peak memory in minutes. A five-minute real-time run at the same rates, with heavy queries running concurrently, measures commit latency and query latency honestly. The two modes share all code except the clock.
8. **Workload profiles are fixed in code.** `small` and `busy` (below). `busy` is the one every threshold is checked against. The design doc's "normal workload" becomes `busy` once measured.
9. **Fault injection through a hook, not build tags.** The flusher has a `Hook func(step string) error`. Tests inject a hook that aborts at a step and then reconcile in-process. The CLI's `crash` command installs a hook that calls `os.Exit(137)` so the shell crash matrix tests a real process death.
10. **Hot window is the current and the previous hour.** At simulated or real `now`, flush every hour `H` with `H + 2h <= now`; at `now = 14:00:00` that flushes `12:00` and everything older and keeps `13:00` and `14:00`. Late rows for already flushed hours produce additional small files; the report counts files per hour so the cost of that trickle is visible.

### Workload profiles

| Profile | Logs/s | Spans/s | Metric points/s | Services | Environments | Metric series |
| --- | --- | --- | --- | --- | --- | --- |
| `small` | 10 | 5 | 5 | 3 | 1 | 50 |
| `busy` | 100 | 50 | 50 | 10 | 2 | 500 |

`busy` is roughly 17 million rows a day and 120 million over seven days. The generator is deterministic from a seed. Spans form traces of 1 to 8 spans rooted at an HTTP server span. Logs reference the trace of the span they belong to about 60% of the time. One percent of logs arrive with timestamps up to three hours late. Metrics are `http.server.request.duration` (explicit-bucket histogram, cumulative, OTel default boundaries), `app.jobs.processed` (monotonic cumulative sum with a reset every simulated 6 hours per service instance), and `process.memory.usage` (gauge). Every series emits one point every 10 simulated seconds, so the series count is ten times the points-per-second rate.

Every generated row has a key that is unique across the whole run so that verification can detect duplication as well as loss: spans use `(trace_id, span_id)`, metric points `(series_hash, ts)`, and logs carry a monotonically increasing `seq` in `attributes`.

A second run on an existing data dir (the real-time run after the accelerated one) continues rather than restarts: it reads `expected.json`, starts `seq` at the total log count so far, and uses a different seed so trace and span IDs come from a fresh random stream (128-bit and 64-bit random IDs do not collide in practice). Cumulative counters start from zero with the new run's `start_ts`, which is exactly a process restart and is handled by the reset rule. `expected.json` counts accumulate across runs.

### Data model

Hot tables, one per signal, mirrored exactly in Parquet. Timestamps are `TIMESTAMP` in UTC. All JSON-bearing columns are `VARCHAR`.

```sql
CREATE TABLE IF NOT EXISTS logs (
  ts TIMESTAMP NOT NULL, observed_ts TIMESTAMP, ingest_ts TIMESTAMP NOT NULL,
  project VARCHAR NOT NULL, service VARCHAR NOT NULL, environment VARCHAR, version VARCHAR,
  severity_number SMALLINT, severity_text VARCHAR, body VARCHAR,
  trace_id VARCHAR, span_id VARCHAR, scope VARCHAR,
  resource VARCHAR, attributes VARCHAR
);
CREATE TABLE IF NOT EXISTS spans (
  ts TIMESTAMP NOT NULL, end_ts TIMESTAMP NOT NULL, ingest_ts TIMESTAMP NOT NULL,
  project VARCHAR NOT NULL, service VARCHAR NOT NULL, environment VARCHAR, version VARCHAR,
  trace_id VARCHAR NOT NULL, span_id VARCHAR NOT NULL, parent_span_id VARCHAR,
  name VARCHAR NOT NULL, kind SMALLINT, status_code SMALLINT, status_message VARCHAR,
  duration_ns BIGINT NOT NULL, scope VARCHAR,
  resource VARCHAR, attributes VARCHAR, events VARCHAR, links VARCHAR
);
CREATE TABLE IF NOT EXISTS metric_points (
  ts TIMESTAMP NOT NULL, start_ts TIMESTAMP, ingest_ts TIMESTAMP NOT NULL,
  project VARCHAR NOT NULL, service VARCHAR NOT NULL, environment VARCHAR, version VARCHAR,
  name VARCHAR NOT NULL, unit VARCHAR, type SMALLINT NOT NULL, temporality SMALLINT,
  monotonic BOOLEAN, series_hash UBIGINT NOT NULL,
  resource VARCHAR, attributes VARCHAR,
  value_int BIGINT, value_double DOUBLE,
  count UBIGINT, sum DOUBLE, min DOUBLE, max DOUBLE,
  bucket_counts UBIGINT[], bucket_bounds DOUBLE[]
);
```

`type`: 1 gauge, 2 sum, 3 histogram. `temporality`: 1 delta, 2 cumulative. `series_hash` is FNV-64a over `name`, the sorted attribute pairs, and `service`.

Manifest (SQLite):

```sql
CREATE TABLE IF NOT EXISTS files (
  id INTEGER PRIMARY KEY,
  signal TEXT NOT NULL,            -- logs | spans | metric_points
  hour TEXT NOT NULL,              -- RFC 3339 UTC hour start, e.g. 2026-10-07T13:00:00Z
  path TEXT NOT NULL UNIQUE,       -- relative to the data dir
  rows INTEGER NOT NULL,
  min_ts TEXT NOT NULL, max_ts TEXT NOT NULL,
  max_ingest_ts TEXT NOT NULL,     -- ingest cutoff: hot rows of this hour at or below it are in this file
  bytes INTEGER NOT NULL,
  schema_version INTEGER NOT NULL,
  created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS files_signal_hour ON files (signal, hour);
```

File layout: `<data>/telemetry/<signal>/date=YYYY-MM-DD/hour=HH/<unix-nanos>-<random-hex>.parquet`. Temporary files use the same name plus `.tmp` in the same directory. Hive-style directory names are kept for human legibility even though the manifest, not the directory, drives queries.

### Flush sequence and crash points

For each `(signal, hour)` with rows in the hot table and `hour + 2h <= now`:

1. `cutoff = SELECT max(ingest_ts) FROM <signal> WHERE ts >= $hour AND ts < $hour + 1h`, then `COPY (SELECT * FROM <signal> WHERE ts >= $hour AND ts < $hour + 1h AND ingest_ts <= $cutoff ORDER BY ts) TO '<tmp>' (FORMAT parquet, COMPRESSION zstd)`, both in one DuckDB transaction so they see the same snapshot — hook step `written`
2. `fsync` the file and its directory, `rename` tmp to final — hook step `renamed`
3. Insert the manifest row with `max_ingest_ts = cutoff` — hook step `recorded`
4. `DELETE FROM <signal> WHERE ts >= $hour AND ts < $hour + 1h AND ingest_ts <= $cutoff` — hook step `deleted`

Reconcile on startup, in this order: remove `*.tmp` files; adopt final-named files missing from the manifest, reading `max(ingest_ts)` from the file as its cutoff; remove manifest rows whose file is missing; for every manifest `(signal, hour)`, delete hot rows of that hour with `ingest_ts <= max(max_ingest_ts)` over that hour's files. Rows that arrived after the cutoff are left alone and flush later. Then retention runs.

The invariant checked after every crash point, per signal: the count of rows in `hot UNION ALL cold` equals the count the generator produced, and the count of distinct row keys equals that count too, so nothing was lost and nothing was duplicated. The manifest paths must match the final-named files on disk one to one.

### Queries

`query.Source(signal, from, to, files) string` returns one SQL subquery: hot rows in range, `UNION ALL`, `read_parquet([files], union_by_name = true)` rows in range, with an explicit column list so the union stays aligned if a column is added later. With no files the subquery is hot only.

Measured queries, all over `[now - 7d, now)` unless stated:

- `count_by_severity`: logs grouped by service and severity for the last 24 h.
- `request_rate`: requests per minute from `http.server.request.duration` counts, last 6 h.
- `p95_latency`: merged-bucket p95 of the duration histogram per service, last 1 h.
- `jobs_rate`: per-minute rate of `app.jobs.processed` with reset handling, last 24 h.
- `trace_by_id`: all spans for one trace ID, scanning the full 7 days.
- `error_logs_page`: 100 most recent error logs for one service with a JSON attribute filter.

Cumulative points become deltas before any aggregation, for sums and histograms alike. Per `series_hash` ordered by `ts`: a point whose `count` (or `value`) is lower than the previous point's, or whose `start_ts` differs from it, is a reset and its delta is its own value; otherwise the delta is the difference from the previous point, element-wise for `bucket_counts`. A point with no previous point in the fetched range has no delta and is dropped. To avoid dropping the first point of every window, queries fetch from `from - 2 * interval` and keep only deltas whose `ts` is inside `[from, to)`; `interval` is a query parameter defaulting to the generator's 10 s, and tests with wider spacing pass their own. Sums read `COALESCE(value_double, value_int::DOUBLE)` so integer counters, which the generator writes to `value_int`, are rated correctly. Delta-temporality points are used as they are. One SQL CTE, `deltas`, implements this and both metric queries build on it.

Counter rate: sum the deltas per `time_bucket(step)`; the result is one row per step with the summed delta, and the overall rate is the total divided by the window. Histogram quantile: sum the delta `bucket_counts` element-wise across series with identical `bucket_bounds`, then interpolate linearly inside the bucket that crosses rank `q * total`: `lower + (upper - lower) * (rank - cumulative_before) / bucket_count`. A rank that lands in the unbounded last bucket returns the last finite bound, as Prometheus does; an empty histogram returns `ok = false`. Series with different bounds are reported, not merged.

### Measurements and thresholds

| Checklist item | How it is measured | Pass threshold |
| --- | --- | --- |
| Crash-safe flush | Shell matrix: for each of the four steps, ingest `small` for 3 simulated hours, crash, reconcile, verify invariant | All four pass |
| Retention reclaims disk | 7-day `busy` run with 3-day retention and a 2 GB ring buffer; every simulated hour sample both manifest bytes and real filesystem usage of the data dir (`hot.duckdb`, its WAL, `tmp/`, `telemetry/`, the manifest) | Filesystem usage never exceeds the limit plus one hour partition plus the hot file; `hot.duckdb` stops growing after the first day; file count stays bounded |
| Ingestion under heavy queries | 5-minute real-time `busy` run on top of the unretained 7-day dataset, with two goroutines looping the six queries | Commit latency p99 under 500 ms; query p99 under 5 s |
| Trace lookup | 100 random trace IDs from the unretained 7-day dataset, full-window scan | p95 under 1 s, otherwise the trace index follow-up is opened |
| Metric semantics | Unit tests with hand-built series and known answers | Exact matches |
| Backup equivalence | Backup after forced flush, restore into a fresh dir, run the six queries on both | Identical result sets |
| Both Linux architectures | CI matrix builds the spike binary and runs its tests | Both green; binary sizes recorded |
| Memory budget | `VmHWM` from `/proc/self/status` at exit of the 7-day and real-time runs, with `memory_limit = 256MB`, `threads = 2` | Under 1 GB; the real number sets the design doc |

### Report

Every CLI run prints one JSON object to stdout with: profile, mode, simulated and wall durations, rows per signal, commits and commit latency percentiles, flush count and durations including the `DELETE` step on its own, files per hour distribution, Parquet bytes per signal, filesystem bytes of the data dir by top-level entry, peak RSS, and per-query latency percentiles when queries ran. The results note is written from these objects.

Time origin: an accelerated run of `D` days starts its simulated clock at `time.Now().Truncate(time.Hour) - D days`, so simulated time ends at roughly wall-clock now. A real-time run on the same data dir then continues from wall-clock now, and every query window of the form `[now - 7d, now)` covers the simulated data without a seam. `ingest_ts` is always the wall clock, stamped by the writer.

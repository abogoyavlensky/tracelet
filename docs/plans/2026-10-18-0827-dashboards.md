# Phase 2 Slice 2: Dashboards — Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Saved, per-project dashboards of metric panels (time series, stat, table) that admins build in the web UI or write as JSON files applied with `tracelet dashboards apply`, and that read tokens view, with a shared time range, shared filters, and auto-refresh at 10 s, 30 s, 1 m, 5 m, 15 m, or off.

**Tech Stack:** Go 1.27, `modernc.org/sqlite` (already a dependency), testify; React, TypeScript, TanStack Query and Router, Tailwind v4, uPlot (already a dependency), vitest. **No new dependencies, Go or npm.**

## Design

### What this slice delivers

```sh
tracelet dashboards apply --project shop --file shop-overview.json   # create or replace, idempotent
tracelet dashboards list --project shop
tracelet dashboards export shop-overview --project shop > shop-overview.json
tracelet dashboards delete shop-overview --project shop --yes
```

In the UI, a fourth view, **Dashboards**, lists the project's dashboards. A dashboard page draws its panels in a grid, all under one time range and one set of service and environment filters, refreshed every 30 s by default. An admin can:
- create a dashboard;
- add the chart they are looking at to a dashboard from the metric page;
- rename, resize, reorder, retype, and remove panels in an edit mode;
- edit a panel's query on the metric page itself;
- delete a dashboard.

A read token sees the same dashboards with no editing controls, and the server refuses its writes.

Out of scope:
- histogram distribution panels, which need a bucket query that does not exist (backlogged in Task 12);
- panels over logs and spans, which need log and span aggregation queries (backlogged in Task 12);
- dashboard edit history;
- draggable layout, which DESIGN already defers.

### Key decisions

1. **A dashboard is one JSON document per project and `uid`.** It is stored as one SQLite row, `definition` as JSON text, keyed `(project_id, uid)`. The `uid` is user-chosen and stable: `^[a-z0-9][a-z0-9-]{0,63}$`. It is what `apply` upserts on, as DESIGN asks ("`apply` is idempotent on stable identifiers"). The UI derives it from the title when creating. Panels are not a separate table. A dashboard is read and written whole, and a dashboard holds at most 30 panels.

2. **"Versioned" means a schema version plus a revision, not history.** `schema_version` (only `1` exists) says how to read the document. Input without it means 1, and any other value is a 400. `revision` is server-managed and starts at 1. It rises by one on every write that changes the definition. A write that changes nothing keeps the revision, so applying the same file twice is a no-op. Edit history is not kept.

3. **Optimistic concurrency through `revision` on PUT.** PUT's body may carry `revision`:
   - **absent:** an unconditional upsert. The CLI's `apply` sends files this way, because `export` strips the revision.
   - **`0`:** create only. If the dashboard exists, the answer is 409. The UI's "New dashboard" sends this.
   - **`N > 0`:** update only if the stored revision is N. Otherwise, including when the dashboard was deleted, the answer is 409 and names the current revision. The UI always sends the revision it loaded, so an edit in one tab never silently clobbers another tab's edit or a CI apply.

   The store implements this as a compare-and-swap `UPDATE … WHERE revision = ?` and an `INSERT` that fails on the primary key. A race between two writers ends in a 409, never in a lost write.

4. **Read tokens read; admin tokens write.** `GET` routes take `read`, which admin also satisfies. `PUT` and `DELETE` take `admin`, as DESIGN says ("Admin tokens manage … dashboards"). A project-scoped read token sees only its project's dashboards through the existing `resolveProject`. The UI hides every editing control unless `session.scope === 'admin'`. The server is the enforcement, and the UI only stays out of the way.

5. **Panels hold a `metric` query object, room for other signals later.** A panel has `id`, `title`, `type`, `width`, `reduce` (stat and table only), and `metric`. The `metric` object holds the existing metric query's fields: `name`, `aggregate`, `group_by`, `service`, `environment`, `attr`, `step`. A later slice can add a sibling such as `logs`, with exactly one set, without changing what `metric` means. Validation is structural:
   - name required;
   - aggregate matches `^(rate|increase|avg|min|max|sum|p[0-9]{1,2}(\.[0-9])?)$`;
   - each `attr` passes `query.ParseAttr`;
   - `step` is a whole-second Go duration of at least `query.MinStep`.

   Whether an aggregation fits the metric's kind depends on the data, so it is checked when the panel runs, and the panel shows the query's 400 message. A dashboard may legitimately name a metric that has not reported yet.

6. **Panel types: `timeseries`, `stat`, `table`.**
   - **Time series:** the existing `MetricChart` with a compact `MetricLegend`.
   - **Stat:** one number. A stat panel may not set `group_by` (400). One number per group is what a table is for.
   - **Table:** one row per group with its label and value, in the server's order, largest first.

   Stat and table take `reduce`:
   - `last`, the default, is the value of the latest *complete* step. A step `[t, t + step)` is complete when `t + step <= range.to` of the response. If no complete step has a value, it is the latest non-null value. This exists because the last step of a counter rate reads low until it completes (DESIGN, Steps).
   - `sum` adds every non-null step value and is allowed only when `aggregate` is explicitly `increase`, which makes it "total over the range" (for example, orders today). Summing rates, averages, or percentiles is meaningless or forbidden ("never average percentiles"), so `reduce` offers nothing else.

   `reduce` on a time series panel is a 400. Histogram distribution panels are out of scope (Task 14).

7. **Layout is a CSS grid, with width in quarters.**
   - The grid is one column on phones, two from `md`, and four from `xl`.
   - `width` is 1 to 4. On `md` a width of 2 or more spans both columns. On `xl` a panel spans `width` columns.
   - The defaults are 2 for time series and table, and 1 for stat.
   - Order is array order. Edit mode moves a panel one place earlier or later with buttons. There is no drag, as DESIGN says ("CSS grid first").

8. **Normalization makes the stored form canonical.** The server fills defaults before storing and returns the normalized form:
   - `schema_version` 1;
   - `last` `"1h"`, which is `query.DefaultLast`;
   - `refresh` `"30s"`;
   - each panel's `width` and `reduce`;
   - a panel `id` where missing.

   A missing id becomes `p<n>` with the smallest positive n that is not taken. Ids match `^[a-z0-9][a-z0-9-]{0,39}$` and are unique within the dashboard. Empty optional strings and empty `attr` lists are omitted (`omitempty`). Two normalized definitions are equal when their `json.Marshal` bytes are equal, which is how decision 2's no-op write is detected. A file hand-written without ids, applied twice, gets the same ids both times.

9. **Dashboard-level range, filters, and refresh.**
   - **Range.** The document holds a default range, `last`. On open, a URL without a range is replaced (`replace: true`) with `last=<default>`, so the header's picker shows the dashboard's range and a copied link is explicit.
   - **Filters.** `service` and `environment` live only in the URL. Each fills a panel's own filter when the panel leaves it empty, and a panel that pins a filter keeps it. So a panel comparing `service=api` still works under a dashboard filter of `web`, and nothing silently empties.
   - **Refresh.** `refresh` is one of `off`, `10s`, `30s`, `1m`, `5m`, `15m`; 30 s is the default. The document's value is the default, and a URL `refresh` overrides it for that view. Panels refetch at that interval while the tab is visible, which is TanStack Query's default. The header's refresh button already invalidates every query and covers manual refresh.

10. **Panels run the existing query endpoint, one request each.** No batch endpoint. The gate queues queries instead of refusing them (`internal/query/gate.go`: `Acquire` waits on the context), and at 30 s refresh a personal dashboard's load is small. Panel queries use the same `['metric', params]` key as the metric page, so they share its cache.

11. **The metric page is the panel query editor.** There is no second query builder.
    - **Add to dashboard.** An admin on `/metrics/$name` gets an "Add to dashboard" popover with these fields: an existing dashboard or a new one, a panel title (default: the metric name), and a type. Stat is disabled while grouped. Adding fetches the dashboard fresh, appends the panel, and PUTs with the fetched revision.
    - **Edit query.** In view mode, an admin's panel menu has "Edit query". It opens `/metrics/$name` with the panel's own query fields, not the dashboard's filters, plus the dashboard range and `dashboard=<uid>&panel=<id>`. The page then shows a bar: "Editing the query of ‹panel› on ‹dashboard›", with Save to panel and Cancel. The bar keeps the panel's `metric` as it was when editing began. Save fetches the dashboard fresh. If that panel's `metric` no longer equals the kept one, Save refuses: "This panel's query changed elsewhere since you started editing; reload". Otherwise it replaces the panel's `metric` in the fresh dashboard, PUTs with the fetched revision, and returns to the dashboard. Edits to other panels in between are kept, a concurrent edit of this query is never overwritten, and the revision check covers the gap between the fetch and the PUT.
    - **Changing the metric name** means adding a new panel and removing the old one.
    - **Open in Metrics.** Everyone's panel menu has "Open in Metrics", which carries the panel's *effective* query, dashboard filters included, for investigation.

12. **The header gains a fourth item.** On `lg` and wider the tabs show icon and label. On `md` they show icons only, with `title` and `aria-label`. The phone tab bar becomes four columns. This is the small step toward DESIGN's "icon rail when phase 2 adds more views" that four items need. A vertical rail is not built.

### Data model

New migration `internal/sqlite/migrations/002_dashboards.sql`:

```sql
CREATE TABLE dashboards (
  project_id TEXT NOT NULL REFERENCES projects(id),
  uid TEXT NOT NULL,                 -- user-chosen, [a-z0-9-], stable across applies
  definition TEXT NOT NULL,          -- normalized JSON: title, schema_version, last, refresh, panels
  revision INTEGER NOT NULL,         -- 1 on create, +1 on each changing write
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  PRIMARY KEY (project_id, uid)
);
```

Go types in `internal/dashboard`. These shapes are shared by the store, the service, and the handler:

```go
type Definition struct {
	Title         string  `json:"title"`
	SchemaVersion int     `json:"schema_version"`
	Last          string  `json:"last"`
	Refresh       string  `json:"refresh"`
	Panels        []Panel `json:"panels"`
}

type Panel struct {
	ID     string       `json:"id"`
	Title  string       `json:"title,omitempty"`
	Type   string       `json:"type"`             // timeseries, stat, table
	Width  int          `json:"width"`            // 1..4
	Reduce string       `json:"reduce,omitempty"` // stat and table: last, sum
	Metric *MetricQuery `json:"metric"`
}

type MetricQuery struct {
	Name        string   `json:"name"`
	Aggregate   string   `json:"aggregate,omitempty"`
	GroupBy     string   `json:"group_by,omitempty"`
	Service     string   `json:"service,omitempty"`
	Environment string   `json:"environment,omitempty"`
	Attr        []string `json:"attr,omitempty"`
	Step        string   `json:"step,omitempty"`
}

type Dashboard struct {
	ProjectID string
	UID       string
	Revision  int
	CreatedAt time.Time
	UpdatedAt time.Time
	Definition
}

// Summary is a list row.
type Summary struct {
	UID       string
	Title     string
	Panels    int
	Revision  int
	UpdatedAt time.Time
}
```

Store interface, in `internal/dashboard`. The SQLite store implements it:

```go
type Store interface {
	List(ctx context.Context, projectID string) ([]Dashboard, error)        // ordered by title, then uid
	Get(ctx context.Context, projectID, uid string) (Dashboard, error)      // ErrNotFound
	Insert(ctx context.Context, d Dashboard) error                          // ErrConflict when (project, uid) exists
	Update(ctx context.Context, d Dashboard, prevRevision int) error        // ErrConflict when no row has prevRevision
	Delete(ctx context.Context, projectID, uid string) error                // ErrNotFound
}
```

Service:

```go
func NewService(store Store, now func() time.Time) *Service
func (s *Service) List(ctx context.Context, projectID string) ([]Summary, error)
func (s *Service) Get(ctx context.Context, projectID, uid string) (Dashboard, error)
// Put validates and normalizes def, then creates or updates per decision 3.
// expect is nil (unconditional), 0 (create only), or N (update if at N).
func (s *Service) Put(ctx context.Context, projectID, uid string, def Definition, expect *int) (d Dashboard, created bool, err error)
func (s *Service) Delete(ctx context.Context, projectID, uid string) error
```

Errors: `dashboard.ErrNotFound`, `dashboard.ErrConflict`, and a `*dashboard.ConflictError{Message}` that matches `ErrConflict` through `Is`, with messages such as "dashboard shop-overview is at revision 4, not 3; reload it and try again" and "dashboard shop-overview already exists". `*dashboard.ValidationError{Message}` mirrors `project.ValidationError`. Messages name the field path, such as `panels[2].metric.name is required`, so a CLI user can find the line.

### HTTP surface

| Route | Scope | Purpose |
| --- | --- | --- |
| `GET /api/v1/dashboards` | read | `project`; `{"items": [{"uid", "title", "panels", "revision", "updated_at"}]}` |
| `GET /api/v1/dashboards/{uid}` | read | `project`; the dashboard |
| `PUT /api/v1/dashboards/{uid}` | admin | `project`; create or replace; 201 created, 200 otherwise; body per below |
| `DELETE /api/v1/dashboards/{uid}` | admin | `project`; 204, or 404 |

The dashboard as GET returns it, and as PUT accepts it:

```json
{"uid": "shop-overview", "revision": 3, "created_at": "...", "updated_at": "...",
 "title": "Shop overview", "schema_version": 1, "last": "6h", "refresh": "30s",
 "panels": [
   {"id": "p1", "title": "Orders", "type": "timeseries", "width": 2,
    "metric": {"name": "orders.created", "aggregate": "rate", "group_by": "service"}},
   {"id": "p2", "title": "Orders in range", "type": "stat", "width": 1, "reduce": "sum",
    "metric": {"name": "orders.created", "aggregate": "increase"}}
 ]}
```

PUT details:
- `uid` in the body is optional, and if present must equal the path's (400).
- `revision` is decision 3.
- `created_at` and `updated_at` are accepted and ignored, so GET output can be PUT back as is.
- Unknown fields are a 400, through the existing `decodeJSON` with `DisallowUnknownFields`, which catches typos in hand-written files.
- The body limit is `maxJSONBody` (1 MB).

Errors use the API's existing form: `{"error": "..."}` with 400, 401, 403, 404, 409, and 413.

### CLI

```
dashboards list [--project P]                       List dashboards
dashboards export <uid> [--project P]               Print a dashboard as a file for apply
dashboards apply --file F [--project P]             Create or replace the dashboard in F (- for stdin)
dashboards delete <uid> --yes [--project P]         Delete a dashboard
```

- **`list`** prints `UID  TITLE  PANELS  REVISION  UPDATED`, or the raw JSON with `--json`.
- **`export`** GETs the dashboard and drops `revision`, `created_at`, and `updated_at`. It decodes into `map[string]json.RawMessage`, deletes those keys, and prints with `json.MarshalIndent` (two spaces) and a final newline. Top-level keys come out sorted. Panel contents keep the server's order. The file therefore diffs cleanly in git and applies unconditionally.
- **`apply`** reads the file, or stdin with `-`, up to 1 MB. It takes `uid` from it and fails with a usage error if there is none. It PUTs the bytes unchanged to `/api/v1/dashboards/{uid}` and prints `applied dashboard <uid> (revision N)`, or the JSON with `--json`.
- **`delete`** without `--yes` is a usage error, per DESIGN ("Destructive actions require an explicit flag").

The CLI does not import `internal/dashboard`, matching `internal/cli/metrics.go`'s rule of declaring the shapes it prints. `rite check-cli` keeps enforcing that the CLI build links no storage.

### Frontend

- **Routes.** `/dashboards` lists dashboards. `/dashboards/$uid` shows one, with search `project`, range, `service`, `environment`, and `refresh`.
- **`web/src/dashboards.ts`** holds the logic that can be wrong silently, with vitest tests:
  - `effectiveMetric(panel, filters)`, decision 9's fill rule;
  - `panelQueryParams(panel, filters, range, project)`, which builds `MetricQueryParams`;
  - `reducedValue(result, reduce)`, decision 6's rule, with the null and empty-step cases;
  - `allowedTypes(metric)`: stat only when ungrouped;
  - `allowedReduces(metric)`: sum only for an explicit `increase`;
  - `spanClass(width)`, which returns literal Tailwind class strings so the classes survive the build;
  - `movePanel(panels, index, delta)`;
  - `slugify(title)`: lower-case, runs of anything outside `[a-z0-9]` become `-`, trimmed of `-`, at most 64 characters, and `dashboard` when empty;
  - `refreshOptions` and `refreshInterval(refresh)`, which returns ms or `false`;
  - `metricFromSearch(name, search)`, the metric page's search as a panel `metric` without project, range, or dashboard keys;
  - `searchFromPanel(panel, range, extra)`, the metric page search for Edit query and Open in Metrics;
  - `sameMetric(a, b)`, the equality check behind decision 11's Save to panel refusal.
- **Components.**
  - `DashboardPanel.tsx` runs one panel's query and draws it by type, with its menu, and shows the edit controls in edit mode.

- **Pages.** `DashboardsPage.tsx` is the list, with New dashboard for admins. `DashboardPage.tsx` is the view, with edit mode.
- **Editing state.** Edit mode keeps a draft `Definition` in component state. Save PUTs `{...draft, revision}`. A 409 shows a notice with a Reload button. A 400 shows the server's message. Cancel discards the draft.

**Files:**
- Modify: `internal/dashboard/dashboard.go`
- Create: `internal/dashboard/dashboard_test.go`

- [ ] **Step 1: `ValidateUID(uid string) error` and `Normalize(def Definition) (Definition, error)`**
  `Normalize` validates and fills defaults per decisions 5, 6, and 8, and returns a new value without mutating the input's slices. The rules:
  - **Title:** trimmed non-empty, at most 200 characters.
  - **`schema_version`:** 0 becomes 1; anything other than 1 is a 400.
  - **`last`:** `""` becomes `"1h"`; otherwise a positive Go duration.
  - **`refresh`:** `""` becomes `"30s"`; otherwise one of `off`, `10s`, `30s`, `1m`, `5m`, `15m`.
  - **Panels:** at most 30.
  - **Panel `id`:** valid and unique when given; assigned `p<n>` otherwise.
  - **Panel `title`:** at most 200 characters.
  - **Panel `type`:** `""` is an error. Require it, since the type changes what the panel means.
  - **Panel `width`:** 0 becomes the type's default; otherwise 1 to 4.
  - **`metric`:** required, with `name` non-empty and at most 255 characters, the aggregate pattern, each `attr` through `query.ParseAttr`, and `step` a whole-second duration of at least `query.MinStep`. `group_by`, `service`, and `environment` are at most 255 characters.
  - **`metric.attr`:** `nil` when empty.
  - **Stat:** `group_by` must be empty.
  - **`reduce`:** stat and table get `"last"` when empty, and only `last` or `sum` are allowed. `sum` requires `metric.aggregate == "increase"`. `reduce` on a time series is an error.

  Error messages carry the field path, such as `panels[1].reduce`.

- [ ] **Step 1: `Service`**
  - **`List`** maps to `Summary`.

  - **`Put`** steps:
    1. Validate the uid.
    2. Normalize.
    3. `Get` the current dashboard.
    4. Apply decision 3.
       - **`expect == 0`, row exists:** a `ConflictError` "already exists".

    6. If the row exists and differs, `Update(d with Revision+1 and UpdatedAt=now, current.Revision)`.
    7. If the row is missing, `Insert` with revision 1 and `created=true`.

    A store `ErrConflict` from the compare-and-swap surfaces as a `ConflictError`: "dashboard X changed while saving; reload it and try again".
  - **`Delete`** passes through.

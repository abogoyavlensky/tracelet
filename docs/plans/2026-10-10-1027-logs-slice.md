**Goal:** Turn the storage spike into product code and ship the first usable path: any OpenTelemetry SDK sends logs to Tracelet over OTLP/HTTP, and a user searches them through the HTTP API and `tracelet logs search`.

## Design

### What this slice delivers

At the end, this works on a fresh machine:

```sh
tracelet serve --data-dir ./data            # prints a one-time admin token on first start
export TRACELET_TOKEN=tl_...                # the admin token from the line above
tracelet projects create shop --name "Shop"
tracelet tokens create --project shop --scope ingest --name "api server"
# an OpenTelemetry SDK is pointed at http://localhost:8080 with that token as a Bearer header
tracelet logs search --project shop --service api --level error --last 30m --json
```

Logs flow: OTLP/HTTP protobuf request → token authenticates and names the project → decode and validate → bounded queue → single writer commits a batch to the hot DuckDB table → the request is acknowledged → hourly flush moves completed hours to Parquet → queries union hot and cold through the manifest. Traces and metrics are decoded by nothing yet, but their hot tables exist so the storage layer ports whole.

Out of scope, each with a backlog entry: OTLP/JSON encoding, OTLP/gRPC, spans and metrics ingestion, the trace index, late-data compaction, the UI explore view, the SQLite job table, backup and restore, heartbeats, attribute redaction rules, and the CLI-only build without DuckDB.

### Key decisions

1. **Storage packages are ported, not rewritten.** The spike's store, writer, manifest, flush, reconcile, retention, and `Source` move into `internal/` under their product names, with the spike-only parts dropped (`Verify`, the metric queries, the generator, scenarios, reports). Behaviour that phase 0 proved stays byte for byte where it can: the ingest-cutoff flush, adoption of orphan files, file-before-manifest deletion in retention.
2. **One SQLite file, `tracelet.sqlite`, for all application state.** Projects, tokens, and the Parquet manifest share one database and one migration sequence. `modernc.org/sqlite` is the product driver (decided here): pure Go, so DuckDB stays the only native dependency, and the app-state workload is tiny. Migrations are embedded `.sql` files applied in order with a `schema_migrations` table; no migration library.
3. **Per-row strictly increasing `ingest_ts`.** The spike stamped a batch; the product stamps each row one microsecond apart. The cutoff rule keeps working unchanged, and `(ts, ingest_ts)` becomes a unique row key that cursor pagination can rely on without a new column. The writer seeds its last stamp at startup from `max(ingest_ts)` across the hot tables, so stamps stay strictly increasing across restarts and a clock that stepped backwards.
4. **Query and flush consistency: pinned snapshot plus cutoff filter (decided here).** A query opens a DuckDB read transaction first, then reads the manifest once: a single `FilesFor` call returns the files for the range together with each file's `max_ingest_ts`, and the per-hour cutoffs are derived from that same list in Go. For every hour present in the hot table that the list also covers, hot rows with `ingest_ts <= that hour's greatest cutoff` are excluded, because the files contain them. The snapshot predates any `DELETE` that follows a manifest insert, and file list and cutoffs come from one read, so a flush can neither duplicate nor hide an hour. Only hours actually present in hot are filtered, which keeps the predicate to a handful of terms.
4a. **Queries and retention exclude each other; flush and queries overlap (decided here).** Retention unlinks Parquet files, and a DuckDB snapshot protects hot rows only, so a query must never have a file deleted under it. Flush, on the other hand, only adds files and deletes hot rows, and the snapshot plus cutoff filter already makes it invisible to queries, so making queries wait for flush (several seconds per hour at the normal workload) would buy nothing. The `Flusher` therefore never takes a lock; the maintenance loop takes the exclusive side only around `ApplyRetention`, which phase 0 measured at about 15 ms. The lock is `query.Gate`, a slot semaphore of 4: a `Snapshot` takes one slot, retention takes all four. Every acquisition selects on the slot and on the caller's context, so a cancelled or expired request returns at once instead of waiting behind maintenance, which a `sync.RWMutex` cannot do. Four slots are also the query concurrency bound the design's resource budget asks for; each snapshot carries a 30 s deadline from the request's start.
5. **Writer batch bounds: 250 ms or 2,000 rows, whichever first, and a submission is never split (decided here).** Phase 0 measured a 5 ms WAL sync per commit and multi-second stalls at 12,000-row commits. At the normal workload this is about four small commits a second. A single request larger than 2,000 rows is committed on its own, in one commit, rather than split: splitting would let a later chunk fail after an earlier one committed, and the client's retry would then duplicate the committed chunk. The 4 MB body limit bounds how large that lone commit can be.
6. **OTLP endpoint at `/v1/logs`, outside `/api/`.** Every OpenTelemetry SDK appends `/v1/logs` to the configured endpoint, so users set `OTEL_EXPORTER_OTLP_ENDPOINT=http://host:8080` and nothing else. The management API stays under `/api/v1/`.
7. **Protobuf only in this slice.** OTLP/JSON encodes trace and span IDs as hex while `protojson` expects base64, so correct JSON support needs custom decoding. The Go, Java, Python, and .NET SDKs default to protobuf. JSON requests get `415` with a message naming the supported encoding and go to the backlog, tagged for the browser and mobile slice.
8. **Flush and retention run from a maintenance ticker, not a jobs table.** The design puts SQLite-backed jobs in phase 3 with alerts. Until then a goroutine owned by the app runs `FlushDue` and `ApplyRetention` once a minute under the maintenance lock, with startup running reconcile then retention first.
9. **Tokens are random, hashed at rest, and scoped.** `tl_` plus 40 hex characters; SQLite stores the SHA-256 and a 6-character prefix for listing. Scopes are `ingest` (one project, write only), `read` (one project or all), `admin` (everything). On first start with no admin token, the server creates one and prints it once; `TRACELET_ADMIN_TOKEN` seeds it instead for containers. Tokens travel only in `Authorization: Bearer`.
10. **Telemetry stores the project ID, the API speaks slugs.** A project has an immutable random ID stored in every telemetry row and a user-chosen slug used in URLs and flags. Renaming a slug never touches telemetry.
11. **The API is described by a hand-written OpenAPI document** at `api/openapi.yaml`, embedded and served at `/api/v1/openapi.yaml`. A test fails when a registered route is missing from it.
12. **The spike is deleted when the port is done**, with its workflow, rite tasks, and ignore lines. The results notes stay and name the last commit that held the code.
13. **CI pins `ubuntu-24.04` and adds the arm64 leg** now that the main module links DuckDB, for the glibc reason the design records.

### Data model additions

Telemetry tables are the spike's three hot tables unchanged (see `docs/plans/2026-10-07-2303-storage-spike.md`), stored in `<data>/hot.duckdb`. Application state in `<data>/tracelet.sqlite`:

```sql
-- 001_initial.sql
CREATE TABLE schema_migrations (version INTEGER PRIMARY KEY, applied_at TEXT NOT NULL);
CREATE TABLE projects (
  id TEXT PRIMARY KEY,                 -- 16 random hex chars, immutable, stored in telemetry rows
  slug TEXT NOT NULL UNIQUE,           -- [a-z0-9-]{1,40}
  name TEXT NOT NULL,
  created_at TEXT NOT NULL
);
CREATE TABLE tokens (
  id TEXT PRIMARY KEY,                 -- 16 random hex chars
  project_id TEXT REFERENCES projects(id),   -- NULL for admin and all-project read tokens
  scope TEXT NOT NULL CHECK (scope IN ('ingest','read','admin')),
  name TEXT NOT NULL,
  prefix TEXT NOT NULL,                -- first 6 chars after tl_, for listing
  hash BLOB NOT NULL UNIQUE,           -- sha256 of the full token
  created_at TEXT NOT NULL,
  last_used_at TEXT,
  revoked_at TEXT
);
CREATE TABLE files ( ...the spike's manifest table, unchanged... );
CREATE INDEX files_signal_hour ON files (signal, hour);
```

### HTTP surface

| Route | Scope | Purpose |
| --- | --- | --- |
| `POST /v1/logs` | ingest | OTLP/HTTP logs, `application/x-protobuf`, optional gzip, 4 MB body limit |
| `GET /api/v1/health` | none | status, version, ingest counters, queue depth, last flush |
| `GET /api/v1/projects`, `POST /api/v1/projects` | admin | list, create |
| `GET /api/v1/tokens`, `POST /api/v1/tokens`, `DELETE /api/v1/tokens/{id}` | admin | list (prefixes only), create (plaintext returned once), revoke |
| `GET /api/v1/logs` | read | search, parameters below |
| `GET /api/v1/services` | read | distinct services with counts in a time range, for discovery |
| `GET /api/v1/openapi.yaml` | none | the API description |

`GET /api/v1/logs` parameters: `project` (slug; required unless the token is project-scoped), `service`, `environment`, `level` (minimum severity: `trace`, `debug`, `info`, `warn`, `error`, `fatal`), `q` (case-insensitive substring of body), `trace_id`, `attr` (repeatable `key:value`, exact match on `json_extract_string(attributes, '$.key')`), `from` and `to` (RFC 3339) or `last` (Go duration), `limit` (default 100, max 1,000), `cursor`. The first page resolves `last` into an absolute `[from, to)` and the cursor carries that range along with the last item's position, so later pages read the same window even though wall-clock time has moved; a request that sends both `cursor` and any of `from`, `to`, `last` is a 400. Response:

```json
{
  "items": [{"ts": "...", "observed_ts": "...", "service": "api", "environment": "prod", "version": "1.4.0",
             "severity_number": 17, "severity_text": "ERROR", "body": "...", "trace_id": "...", "span_id": "...",
             "scope": "...", "resource": {"...": "..."}, "attributes": {"...": "..."}}],
  "next_cursor": "opaque or absent",
  "range": {"from": "...", "to": "..."},
  "limit": 100,
  "truncated": true
}
```

Ordering is newest first by `(ts, ingest_ts)`. The cursor is the URL-safe base64 of a small JSON object: the last item's `ts` and `ingest_ts`, and the page's `from` and `to`; the next page is `(ts, ingest_ts) < cursor` within that range. `truncated` is true when a `next_cursor` exists. Errors are `{"error": "..."}` with 400, 401, 403, 404, 413, 415, 503 as appropriate; 503 carries `Retry-After: 1`.

### Ingestion path

`ingest.Ingester` owns a bounded channel of submissions (default 256) and one writer goroutine. `Submit(ctx, batch)` blocks until the batch's commit completes or `ctx` ends, and returns `ErrOverloaded` immediately when the channel is full. The writer goroutine drains submissions into one commit when 2,000 rows are pending or 250 ms have passed since the first pending submission, calls `Writer.Write`, then completes every submission in the commit with the same result. A submission is never split across commits: one larger than 2,000 rows is committed alone. Disk pressure is enforced before the queue: the maintenance loop samples free disk every tick and sets an atomic flag when it is under `DiskFloorBytes`; while the flag is set the OTLP handler answers 503 with `Retry-After: 30` and a message naming disk pressure, and health reports it. Counters (accepted rows, rejected rows, overloaded requests, commits, queue depth, last commit time and latency) are read by the health handler. Shutdown: the HTTP server stops accepting, the ingester drains what is queued, the writer closes, then DuckDB closes.

The OTLP handler: authenticate (`ingest` scope), reject on disk pressure, check `Content-Type`, enforce the 4 MB limit on the decompressed bytes (the raw body is capped too, and a gzip stream that expands past the limit is a 413), `proto.Unmarshal` into `ExportLogsServiceRequest`, convert, submit, respond with an `ExportLogsServiceResponse` whose `partial_success` names rejected records and the reason. Conversion rules: `ts` is `time_unix_nano`, or `observed_time_unix_nano` when zero; records with both zero are rejected; `service` is the resource's `service.name` or `unknown_service`, counted on health; `environment` from `deployment.environment.name`, `version` from `service.version`; `body` is the string value, or the JSON encoding of any other value kind; `resource` and `attributes` are JSON objects with OTLP `AnyValue`s converted to JSON values; trace and span IDs are lower-case hex or empty.

```
cmd/tracelet/main.go                 serve plus every CLI command, dispatching to internal/cli

internal/otlp/                       decode and convert OTLP logs; partial success
internal/ingest/                     Ingester: bounded queue, batching writer loop, counters
internal/httpapi/                    routes, auth middleware, handlers, JSON and protobuf writers
```

Go style follows `/go-style`: explicit wiring in `internal/app`, consumer-side interfaces only where a fake is needed (`httpapi` consumes small interfaces for the project service and the ingester), SQL as constants, testify in external test packages, storage tests on real DuckDB and SQLite in `t.TempDir()`.

### Testing strategy

Each package keeps the spike's tests where the code is ported. New behaviour gets unit tests at the package boundary. One end-to-end test in `internal/app` starts the whole app on a loopback port, bootstraps the admin token, creates a project and an ingest token through the API, posts a real `ExportLogsServiceRequest` built with the OTLP proto types, and searches the logs back with a read token, including a page boundary. The consistency protocol gets a test that pauses a flush between `recorded` and `deleted` with the hook and asserts a concurrent search returns each row once.

# Phase 1 Slice 2: Spans In, Traces Out — Implementation Plan

**Status: completed** (11 October 2026, branch `traces-slice`). Summary at the end.

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Any OpenTelemetry SDK sends spans to Tracelet over OTLP/HTTP, and a user gets a whole trace by ID, searches spans, and finds the trace's logs, through the HTTP API and `tracelet traces get` / `tracelet spans search`, with trace lookup under one second over seven days of data.

**Tech Stack:** Go 1.27, `github.com/duckdb/duckdb-go/v2` v2.10506.0 (DuckDB 1.5.6), `modernc.org/sqlite`, `go.opentelemetry.io/proto/otlp` v1.11.1 (`trace/v1`, already a dependency), testify. No new dependencies. No frontend work.

## Design

### What this slice delivers

At the end, this works against a server set up as in the README quickstart:

```sh
# an OpenTelemetry SDK is pointed at http://localhost:8080 with an ingest token;
# it appends /v1/traces and /v1/logs itself
tracelet spans search --project shop --service api --root --min-duration 500ms --last 1h
tracelet traces get 4bf92f3577b34da6a3ce929d0e0e4736 --project shop
tracelet logs search --project shop --trace-id 4bf92f3577b34da6a3ce929d0e0e4736 --from <trace start> --to <trace end>
tracelet services --project shop --last 24h            # now counts logs and spans
```

Spans flow exactly as logs do: OTLP/HTTP protobuf request → token names the project → decode and validate → convert into `telemetry.Span` rows → bounded queue → the single writer drops spans already in the hot window, commits the rest → acknowledged → hourly flush to Parquet → queries union hot and cold through a `query.Snapshot`. What is new in the storage layer is the shape of the span Parquet files, which is what makes trace lookup fast (below).

Out of scope, unchanged from the logs slice and its backlog entries: OTLP/JSON, OTLP/gRPC, metrics, late-data compaction, the UI, backup. Also out of scope here: a trace response that embeds the trace's logs (two calls do it, and the trace response carries the range to pass), span aggregations (latency percentiles belong with metrics and the overview), and `trace_state` and the OTLP `flags` field, which are dropped.

### Key decisions

1. **The trace index is the span Parquet file itself, sorted by trace ID with small row groups (decided here; resolves the design's open decision).** Phase 0 measured a 7-day trace lookup at p95 1.03 s alone and 1.8 s under load, scanning the `trace_id` column of 168 hour files (about 940 MB). The design's fallback was "a small per-partition index file listing trace ID and time range, written at flush". A sidecar file would be found by the same mechanism a sorted main file is: Parquet row-group min/max statistics, which DuckDB uses to skip row groups whose `[min, max]` does not contain the looked-up ID. Sorting the hour's spans by `trace_id` makes every row group a disjoint lexicographic range, so a lookup reads the footer and at most one row group per file, and the sidecar buys nothing but a second file to flush, record, reconcile, back up, and retain. The span `COPY` therefore becomes `ORDER BY trace_id, ts` with `ROW_GROUP_SIZE 10000`: at the `busy` workload an hour of spans is about 180,000 rows, so 18 row groups, and a 7-day lookup touches about 168 × 10,000 `trace_id` values instead of 30 million. Logs and metric files are untouched; they stay sorted by `ts` with default row groups. The memory follow-up measured `ROW_GROUP_SIZE 30000` as 20% slower to flush on logs; spans are a quarter of the rows at `busy`, so the cost is bounded, and the span file's `ts` ordering only matters within one hour, which the manifest already prunes to. The lookup still needs a time range: it defaults to the last 7 days and the caller may widen it, as the design says. **This decision is verified, not assumed:** Task 11 is an opt-in benchmark that builds 7 days of `busy`-shaped span files through the real flush and measures 100 lookups. If p95 is not under 1 s, the executor tries `ROW_GROUP_SIZE 5000` once; if that misses too, the executor stops there and reports, and the fallback is a new plan, not an improvisation. The size that passed is the one the design records.

2. **Span deduplication happens in the writer, against the hot window (decided here, as the design specifies).** A lost response after a commit makes the SDK retry the whole request. Before appending, the writer drops any span whose `(project, trace_id, span_id)` is already in the hot `spans` table or earlier in the same batch, with one `SELECT project, trace_id, span_id FROM spans WHERE trace_id IN (...) AND ts BETWEEN ...` over the batch's distinct trace IDs and time span, inside the write transaction. The project is part of the key because one commit can hold submissions from several projects, and the same IDs in two projects are two different spans. Duplicates are counted (`duplicate_spans` on health), never silently absorbed into row counts. A retry that arrives after the hour was flushed is not caught; the design accepts this and the README says so. Logs are not deduplicated, as decided.

3. **One OTLP handler, two routes.** `/v1/traces` and `/v1/logs` share everything but decoding and conversion: scope check, disk pressure, content type, body limits, gzip, submit, error mapping, partial success. The handler becomes a generic `otlpIngest` over a small per-signal conversion function. `ExportTraceServiceResponse` has the same wire layout as the logs response (`partial_success` = 1, `rejected_spans` = 1, `error_message` = 2), so `otlp.PartialSuccess` serves both. Requests decode into `tracepb.TracesData`, wire-identical to `ExportTraceServiceRequest`, keeping the gRPC-importing collector package out of the build, as for logs.

4. **Span conversion rules.** `ts` is `start_time_unix_nano`; a span without it, or with any timestamp past `int64` nanoseconds, is rejected with a reason. `end_ts` is `end_time_unix_nano`, or `ts` when zero; `duration_ns` is `end_ts - ts`, floored at 0 when the end precedes the start. A `trace_id` that is not 16 bytes or a `span_id` that is not 8 bytes is rejected (the OTLP spec requires both). `parent_span_id` is hex or empty. Service, environment, version, and the resource JSON follow the logs rules exactly through a shared helper. `kind` and `status_code` are stored as the OTLP enum numbers; `status_message` as is. Events are a JSON array of `{"ts": RFC 3339 nano, "name": ..., "attributes": {...}}`; links are a JSON array of `{"trace_id": hex, "span_id": hex, "attributes": {...}}`; both omit `attributes` when empty and are NULL when there are none. `trace_state`, `flags`, and the `dropped_*_count` fields are dropped.

5. **Trace retrieval: `GET /api/v1/traces/{trace_id}`.** The ID must be 32 hex characters (case-insensitive, stored and compared lower-case); anything else is a 400. The range comes from `from`/`to`/`last` and defaults to the last 7 days, where logs default to the last hour. Spans come back oldest first by `(ts, ingest_ts)`, flat, with `parent_span_id` for the client to nest, capped at `MaxTraceSpans = 5000` with `truncated: true` past that. The response carries `start` (earliest `ts`), `end` (latest `end_ts`), `duration_ns`, `services`, and the effective `range`, so a client can bound the follow-up logs search. These four describe the spans returned, not the whole trace: when `truncated` is true the later part of the trace is missing from them too, and the OpenAPI description says so. A trace over 5,000 spans is far outside the personal-project workload, so a second whole-trace aggregate is not worth a query on every lookup. No span in range is a 404 naming the range, since a trace older than 7 days is found by widening it.

6. **Span search: `GET /api/v1/spans`, mirroring logs search.** The vision's phase 1 is "logs and traces exploration with correlation", and a trace ID has to come from somewhere other than a log. Filters: `service`, `environment`, `name` (exact), `status` (`unset`, `ok`, `error`), `min_duration` (Go duration), `root` (`true`: `parent_span_id IS NULL`), `trace_id`, repeatable `attr`, and the same range, `limit`, and cursor rules as logs. Newest first by `(ts, ingest_ts)`, the same cursor shape. Items are full span objects, the same schema the trace response uses. "Traces search" is `spans?root=true`, documented as such: a trace whose root span was never exported does not appear there, which is honest about what the data holds.

7. **`GET /api/v1/services` counts spans too.** `items[].spans` joins `items[].logs`; busiest first by the sum. Adding a field is backward compatible.

8. **Range defaults become a parameter.** `query.ResolveRange` gains a `defaultLast` argument (logs and spans pass one hour, traces seven days) instead of a second function.

### Data model

No schema change. The `spans` hot table and Parquet columns are the ones the logs slice created (`internal/duckdb/store.go`, `internal/query/source.go`); this slice is the first to write them. No SQLite migration.

### HTTP surface

| Route | Scope | Purpose |
| --- | --- | --- |
| `POST /v1/traces` | ingest | OTLP/HTTP traces, `application/x-protobuf`, optional gzip, 4 MB limit; same rules as `/v1/logs` |
| `GET /api/v1/traces/{trace_id}` | read | one trace, parameters `project`, `from`, `to`, `last` (default 7 days) |
| `GET /api/v1/spans` | read | span search, parameters below |
| `GET /api/v1/services` | read | unchanged route; items gain `spans` |
| `GET /api/v1/health` | none | `ingest` gains `duplicate_spans` |

`GET /api/v1/spans` parameters: `project` (as for logs), `service`, `environment`, `name`, `status` (`unset` | `ok` | `error`), `min_duration` (Go duration, e.g. `500ms`), `root` (`true`), `trace_id`, `attr` (repeatable `key:value`), `from`/`to` or `last`, `limit` (default 100, max 1,000), `cursor`. Same cursor and range rules as logs.

Span object, shared by both responses:

```json
{"ts": "...", "end_ts": "...", "duration_ns": 120000000, "service": "api", "environment": "prod", "version": "1.4.0",
 "trace_id": "4bf9...", "span_id": "00f0...", "parent_span_id": "...", "name": "GET /cart",
 "kind": 2, "status_code": 2, "status_message": "deadline exceeded", "scope": "...",
 "resource": {"...": "..."}, "attributes": {"...": "..."}, "events": [...], "links": [...]}
```

Trace response:

```json
{"trace_id": "4bf9...", "start": "...", "end": "...", "duration_ns": 120000000,
 "services": ["api", "worker"], "spans": [...], "range": {"from": "...", "to": "..."}, "truncated": false}
```

Spans page: `{"items": [...], "next_cursor": "...", "range": {...}, "limit": 100, "truncated": true}`, as for logs.

Errors as for logs: `{"error": "..."}` with 400, 401, 403, 404, 413, 415, 503 (`Retry-After`).

### Writer deduplication

`duckdb.Writer.Write` gains a step between `BEGIN` and the appends: when the batch has spans, collect the distinct trace IDs and the min and max `ts`, run `SELECT project, trace_id, span_id FROM spans WHERE ts >= ? AND ts <= ? AND trace_id IN (?, ?, ...)` on the writer's connection (inside the transaction, so it sees every earlier commit), and build the set of existing `(project, trace_id, span_id)` keys. Append a span only if its key is neither in that set nor already appended from this batch. The caller's batch is not mutated. `CommitStats` gains `Duplicates int`; `Rows` counts appended rows. The ingester adds `Duplicates` to a new `duplicateSpans` counter, exposed as `duplicate_spans` in `ingest.Stats`. At the `busy` workload this is one query over about 360,000 hot rows per commit, four times a second, bounded by the `ts` range; if that ever measures as a problem the lever is a narrower range, not removing the check.

### Testing strategy

Package tests at each boundary, as in the logs slice: conversion against hand-built `tracepb` messages; dedup on a real DuckDB store; the `COPY` statement string plus a real flush whose Parquet metadata shows the row groups and the trace-ID order; queries over an env with one cold hour and one hot hour, including a trace that straddles the two; handlers with the fake auth and ingester; the CLI against a fake API; and the end-to-end test extended with a traces scenario (a trace across two services with a correlated log record, exported twice). The benchmark is a test skipped unless `TRACELET_BENCH=1`, so `rite check` stays fast.
